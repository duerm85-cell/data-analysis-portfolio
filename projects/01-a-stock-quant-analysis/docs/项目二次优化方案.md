# 《A 股量化数据工程平台》二次优化方案

> 项目定位：面向校招/实习的数据分析、数据开发、量化数据开发作品集。
> 优化原则：不靠堆数据量和复杂组件制造“规模感”，而是用清晰的数据分层、按需查询、预聚合、缓存、质量监控和诚实的数据口径，呈现一个可扩展的数据产品 Demo。

## 0. 结论摘要

### 是否继续只展示 50 只股票？

**不建议把 50 只股票继续作为系统对外呈现的全部数据规模，但也不建议直接把 50 万行完整宽表加载到 Streamlit。**

推荐采用三层公开 Demo：

1. **全市场资产目录层**：展示完整股票池元数据和全市场统计，数据量小，启动时加载。
2. **分析汇总层**：提前生成市场、行业、质量、因子 IC 等汇总表，页面直接查询，避免在线扫描全量宽表。
3. **交互明细层**：保留 150～300 只代表性股票、最近 1～3 年的合成或合规样本行情；用户选择股票和日期后再按需查询。

这比“50 只全部读入内存”更有规模感，也比“5000 只、数百万行全部塞进网页”更接近真实企业数据平台。

### 最终推荐架构

```text
                           ┌─ dim_stock：全市场股票目录/行业/板块
本地真实流水线 ──发布任务──┼─ fact_market_daily：每日市场汇总
                           ├─ fact_industry_daily：行业日度汇总
                           ├─ fact_factor_ic_daily：因子 IC 汇总
                           ├─ fact_data_quality_run：质量检测历史
                           ├─ fact_stock_daily_demo：按需查询的公开明细
                           └─ manifest：真实研究规模与公开数据口径
                                           │
                                           ▼
                                 SQLite 只读查询服务层
                                           │
                              st.cache_data 参数化结果缓存
                                           │
                                           ▼
                                    Streamlit 页面
```

### 不建议现在增加的组件

- 不上 Kafka、Flink、Airflow 集群、Kubernetes。
- 不为了 50 万行数据引入微服务。
- 不在 Streamlit 每次访问时请求全部股票实时行情。
- 不把 Tushare Token 放到前端或仓库。
- 不允许公网用户直接执行任意 SQL。

SQLite + Parquet + 离线发布脚本足以支撑这个作品集，并且更容易解释、测试和部署。

## 1. 当前问题

### 1.1 数据展示规模与真实研究规模不一致

当前公开版只有 50 只合成股票、约 3 年数据。它运行快、合规风险低，但面试官容易误以为整个项目只处理了这一点数据。

实际上应区分三个口径：

| 口径 | 含义 | 首页如何展示 |
|---|---|---|
| 全市场资产目录 | 系统能够识别的 A 股证券及行业信息 | “资产目录：实际条数” |
| 本地研究覆盖 | 完整本地流水线实际验收的数据 | “研究覆盖：364 只、562,789 条、2020-01-07～2026-08-28” |
| 公开交互样本 | 在线可逐股查看的合成/合规样本 | “在线明细：实际条数，演示数据” |

不能把 364 只写成 5000+，也不能把公开 50 只说成全市场。规模感应来自**清晰的资产分层与真实的运行清单**，不是放大数字。

### 1.2 当前 Streamlit 仍以全表 DataFrame 为中心

现有 `app_pro.py` 中：

- `load_data()` 使用 `st.cache_resource` 读取整张 `all_factors.parquet` 或执行 `SELECT * FROM factors`。
- 公开模式也会一次性读取完整 `portfolio_factors.parquet`。
- 市场、因子、情绪等页面从同一个全表 DataFrame 继续做筛选、`groupby`、相关系数和 IC 计算。
- 缓存虽然避免了重复读盘，却把大宽表长期放在进程内存中；数据更新后的失效规则也不够明确。

50 只股票时问题不明显；50 万行、几十个因子时，会增加冷启动时间、内存占用和页面计算延迟。

### 1.3 SQLite 索引主要支持逐股查询，未完整支持 BI 查询

当前已有：

- `daily_data(code, date)`
- `factors(code, date)`
- `sentiment(code, date)`
- `factors` 的 `(code, date)` 唯一索引

这适合“查某只股票一段时间”，但以下查询还缺少专门设计：

- 某个交易日的全市场快照。
- 某个行业的股票筛选。
- 行业在一段时间内的聚合趋势。
- 质量检测运行历史。
- 因子 IC 的日度/月份汇总。

另外，`factors(code, date)` 普通索引和唯一索引语义重复，应保留唯一索引，避免重复维护。

### 1.4 页面数量多，但“数据分析产品主线”不够集中

当前 8 个页面覆盖很全，但存在信息分散：

- “数据平台”和“系统概览”可以合并成资产驾驶舱。
- “市场总览”和“数据洞察”有部分重复。
- “模型预测”容易让人误以为目标是荐股。
- “情绪分析”更适合作为股票画像或因子研究的一部分。
- 数据质量、数据血缘和查询优化虽然是项目强项，却没有成为核心导航。

### 1.5 公开数据合规与真实性之间存在张力

直接上传完整真实逐日行情可能涉及数据源使用、再分发条款和仓库体积问题；完全合成数据又会降低业务真实感。应把“真实元数据、真实汇总、公开样本、合成明细、研究摘要”分开治理，并在页面显示口径。

## 2. 优化目标

### 2.1 产品目标

让面试官在 60 秒内看到：

- 系统处理过多大规模的数据。
- 数据从哪里来、经过哪些层、最后由谁消费。
- 数据新鲜度、质量和异常是否可观测。
- 页面为什么快：预聚合、索引、按需查询和缓存。
- 研究结论是否可信：时间切分、T+1、交易成本与基准。

### 2.2 性能目标

建议设定可测量的验收指标：

| 指标 | 目标 |
|---|---|
| 冷启动到首页可见 | 5～10 秒以内（Streamlit 免费实例唤醒时间另计） |
| 已唤醒：首页刷新 | 2 秒以内 |
| 股票代码/行业下拉加载 | 500 毫秒以内 |
| 单只股票 1～3 年明细查询 | 1 秒以内 |
| 市场/行业图表切换 | 1～2 秒以内 |
| 单次明细返回量 | 默认不超过 1,000 行 |
| 公开应用内存 | 不常驻完整 50 万行宽表 |

### 2.3 可信度目标

- 首页同时显示“研究规模”和“公开交互规模”。
- 每张图标记数据日期、数据来源和是否合成。
- 所有统计口径来自发布清单或预计算表，不在页面中写死。
- 所有外部筛选条件通过参数化 SQL 查询。
- 任意公开查询都有行数、日期范围和超时边界。

## 3. 公开 Demo 数据架构设计

### 3.1 方案比较

#### 方案 A：完整资产元数据 + 热门股票明细 + 历史按需查询

**设计**

- 全量加载一行一股票的资产目录。
- 对 150～300 只代表性股票保留公开明细。
- 用户选定代码、日期范围后查询 SQLite，而不是读取全表。
- 首页和行业页读取离线汇总表。

**优点**

- 用户看到的股票目录和行业结构更接近真实业务。
- 明细加载量受控，交互速度快。
- 很容易解释“冷热数据分层”和“按需加载”。
- 仍可使用当前 SQLite/Streamlit 技术栈。

**缺点**

- 需要确认股票名称、行业、上市日期等元数据是否允许公开再分发。
- 用户选择不在公开明细集内的股票时，需要清楚提示“目录可见、明细未公开”。
- 若在线动态请求实时 API，会增加失败率、Token 管理和限流问题。

**适合度：高。** 这是最适合校招作品集的基础方案。

#### 方案 B：离线数据索引 + SQLite 查询 + 分页加载

**设计**

- 把公开数据写入 SQLite。
- 建立 `(code,date)`、`date`、行业等索引。
- 表格查询必须带日期、股票/行业过滤和 `LIMIT/OFFSET` 或游标条件。
- 所有大计算提前生成汇总表。

**优点**

- 工程能力最直观：表设计、索引、查询计划、分页、参数化查询。
- 50 万行对 SQLite 并不大，只要不 `SELECT *` 全表，响应可以很好。
- 可用 `EXPLAIN QUERY PLAN` 在面试中证明索引生效。

**缺点**

- GitHub/Streamlit 部署需要控制数据库文件大小。
- `OFFSET` 很大时会变慢；需要用 `(date,code)` 游标分页或限定最大页数。
- SQLite 适合单机读多写少，不应包装成高并发生产数据库。

**适合度：高。** 应作为查询服务层实现。

#### 方案 C：数据分层缓存

**设计**

- L0：SQLite/Parquet 持久层。
- L1：`st.cache_data` 查询结果缓存。
- L2：`st.session_state` 保存当前用户的筛选与小型结果。
- 汇总表在发布前离线计算，不依赖首次访问临时生成。

**优点**

- 切页和重复筛选明显加快。
- 无需部署 Redis 等额外服务。
- 缓存边界可以和查询参数、数据版本关联。

**缺点**

- 缓存设置错误会返回旧数据或占用过多内存。
- 缓存不能代替正确的 SQL 和预聚合。
- Streamlit 免费实例重启后缓存会丢失。

**适合度：高。** 但它是 A/B 的配套策略，不是独立的数据架构。

### 3.2 推荐：A + B + C 的轻量组合

不选择单一方案，而是组合为：

```text
全量轻元数据（A）
        +
预聚合表与按需 SQLite（B）
        +
参数化结果缓存（C）
```

#### 公开数据的建议规模

| 数据集 | 建议规模 | 说明 |
|---|---:|---|
| `dim_stock` | 实际可合法发布的完整股票目录 | 一只股票一行，体积很小 |
| `fact_market_daily` | 3～6 年 × 每日一行 | 市场宽度、成交额、涨跌分布 |
| `fact_industry_daily` | 3 年 × 约 30～100 行业 × 每日 | 行业轮动和热力图 |
| `fact_factor_ic_daily` | 3 年 × 10～20 因子 × 每日 | 因子有效性趋势 |
| `fact_stock_daily_demo` | 150～300 只 × 1～3 年 | 约 11 万～23 万行，按需查询 |
| `fact_data_quality_run` | 最近 30～100 次运行 | 质量趋势、异常项和数据水位 |

150～300 只是在线可交互明细的合理范围，不是系统能力上限。页面应明确：“资产目录 N 只；本地研究 364 只；在线交互样本 M 只”。

### 3.3 代表性股票如何选择

不要写“热门股票”却没有规则。生成发布数据包时使用可复现规则，例如：

- 沪市主板、深市主板、创业板、科创板按比例抽样。
- 行业分层抽样，每个一级行业保留固定数量。
- 保证不同市值组、流动性组有代表样本。
- 固定随机种子，输出 `selection_rule` 和选中代码列表到 manifest。

如果明细仍是合成数据，合成代码不要和真实证券名称混配，以免让用户误以为是真实行情。可以使用 `DEMO0001` 或在页面明显标记“模拟代码”。

## 4. 公开数据与真实数据不能上传的解决方案

### 4.1 可选方式比较

| 方式 | 真实性 | 稳定性 | 开发复杂度 | 合规风险 | 校招适合度 |
|---|---:|---:|---:|---:|---:|
| 全量真实行情直接上传 | 高 | 高 | 低 | 高/需确认许可 | 低 |
| 真实股票元数据 + 合成历史明细 | 中高 | 高 | 低 | 中/仍需确认元数据许可 | 高 |
| 真实的汇总指标 + 合成逐股明细 | 中高 | 高 | 中 | 较低/需确认汇总发布边界 | 很高 |
| 用户输入代码，后端实时请求 API | 高 | 中低 | 中高 | 取决于数据源条款 | 中 |
| 只展示静态截图/CSV 摘要 | 中 | 很高 | 低 | 低 | 中低 |
| 自建云数据库存真实数据 | 高 | 中 | 高 | 仍不能绕过数据许可 | 低 |

### 4.2 最推荐的公开口径

采用“**真实研究清单 + 可合规元数据 + 真实/脱敏汇总 + 合成明细**”：

1. `research_manifest.json` 保存本地真实流水线的规模、日期、字段数、质量结论和运行时间，不包含逐日行情。
2. 股票基本信息只在数据源条款允许时公开；否则使用交易所公开名单或只发布行业/板块聚合，不默认把 Tushare 元数据当成可再分发数据。
3. 市场和行业指标若允许发布，保存离线聚合结果，不发布逐股原始行情。
4. 逐股交互明细继续使用确定性合成数据，页面永久显示“演示”。
5. 模型权重、逐笔预测、每日持仓和 Token 继续只保留本地。

这套设计的面试价值在于：你不是因为“传不上 GitHub”被迫删数据，而是在做**数据发布分级、最小化披露和服务层设计**。

### 4.3 是否采用后端动态请求实时行情？

校招项目中可以做成 P2 可选功能，但不建议作为主链路。

**优点**

- 用户能查询指定股票的近期真实行情。
- 页面看起来更“活”。
- 可展示密钥管理、限流、失败降级和缓存。

**缺点**

- Streamlit Cloud 到数据源的网络可能不稳定。
- Tushare Token 必须放在 Streamlit Secrets，不能出现在浏览器或日志。
- API 有积分、频率、可用性和再展示条款限制。
- 每次用户交互都依赖第三方，面试现场更容易失败。
- 实时请求不解决历史分析和规模展示问题。

**结论**：主页面使用稳定的离线快照；若确认条款允许，再加一个“最新行情实验”页或按钮，设置 15～60 分钟 TTL、请求频率限制、失败时回退到快照，并明确时间戳。

## 5. 数据库设计调整

### 5.1 建议的数据模型

#### `dim_stock`：股票维表

```sql
CREATE TABLE dim_stock (
    code          TEXT PRIMARY KEY,
    name          TEXT,
    market        TEXT NOT NULL,
    board         TEXT,
    industry_l1   TEXT,
    list_date     TEXT,
    is_demo       INTEGER NOT NULL DEFAULT 0,
    has_detail    INTEGER NOT NULL DEFAULT 0,
    source        TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
```

用途：启动时只读取这张小表，用于资产数量、行业分布和股票选择器。`has_detail` 告诉页面该股票是否有在线明细。

#### `fact_stock_daily_demo`：公开日线/因子明细

```sql
CREATE TABLE fact_stock_daily_demo (
    code          TEXT NOT NULL,
    date          TEXT NOT NULL,
    open          REAL,
    high          REAL,
    low           REAL,
    close         REAL,
    volume        REAL,
    amount        REAL,
    ret           REAL,
    ma5           REAL,
    ma20          REAL,
    rsi           REAL,
    macd          REAL,
    volatility_20d REAL,
    sentiment     REAL,
    data_version  TEXT NOT NULL,
    PRIMARY KEY (code, date)
) WITHOUT ROWID;
```

用途：按代码和日期范围查询。公开表只保留页面实际使用的列，不复制本地 50 列完整宽表。

#### `fact_market_daily`：市场日度汇总

```sql
CREATE TABLE fact_market_daily (
    date               TEXT PRIMARY KEY,
    stock_count        INTEGER NOT NULL,
    advancing_count    INTEGER NOT NULL,
    declining_count    INTEGER NOT NULL,
    flat_count         INTEGER NOT NULL,
    total_amount       REAL,
    median_return      REAL,
    limit_up_count     INTEGER,
    limit_down_count   INTEGER,
    source             TEXT NOT NULL,
    updated_at         TEXT NOT NULL
);
```

#### `fact_industry_daily`：行业日度汇总

```sql
CREATE TABLE fact_industry_daily (
    industry_l1       TEXT NOT NULL,
    date              TEXT NOT NULL,
    stock_count       INTEGER NOT NULL,
    average_return    REAL,
    median_return     REAL,
    total_amount      REAL,
    advancing_ratio   REAL,
    PRIMARY KEY (industry_l1, date)
) WITHOUT ROWID;
```

#### `fact_factor_ic_daily`：因子效果汇总

```sql
CREATE TABLE fact_factor_ic_daily (
    factor_name       TEXT NOT NULL,
    date              TEXT NOT NULL,
    ic                REAL,
    sample_count      INTEGER,
    PRIMARY KEY (factor_name, date)
) WITHOUT ROWID;
```

#### `fact_data_quality_run` 与 `fact_data_quality_issue`

```sql
CREATE TABLE fact_data_quality_run (
    run_id              TEXT PRIMARY KEY,
    started_at          TEXT NOT NULL,
    data_date           TEXT,
    row_count           INTEGER,
    stock_count         INTEGER,
    duplicate_key_count INTEGER,
    invalid_ohlc_count  INTEGER,
    unexpected_missing  INTEGER,
    quality_score       REAL,
    status              TEXT NOT NULL
);

CREATE TABLE fact_data_quality_issue (
    run_id        TEXT NOT NULL,
    rule_name     TEXT NOT NULL,
    column_name   TEXT,
    issue_count   INTEGER NOT NULL,
    severity      TEXT NOT NULL,
    message       TEXT,
    PRIMARY KEY (run_id, rule_name, column_name)
);
```

用途：质量页不再只有当前一个柱状图，而能展示数据水位、质量评分和规则趋势。

#### `pipeline_run`：流水线运行记录

```sql
CREATE TABLE pipeline_run (
    run_id          TEXT PRIMARY KEY,
    pipeline_name   TEXT NOT NULL,
    started_at      TEXT NOT NULL,
    finished_at     TEXT,
    status          TEXT NOT NULL,
    input_rows      INTEGER,
    output_rows     INTEGER,
    data_start_date TEXT,
    data_end_date   TEXT,
    source          TEXT,
    error_message   TEXT
);
```

用途：给数据血缘和运行监控提供证据，而不只是画一张静态流程图。

### 5.2 索引设计

```sql
-- 主键已覆盖“某股票 + 日期范围”查询，无需再建重复的普通索引
-- PRIMARY KEY (code, date)

-- 某交易日全市场截面
CREATE INDEX idx_stock_daily_date
ON fact_stock_daily_demo(date);

-- 股票目录按行业筛选并返回代码
CREATE INDEX idx_stock_industry_code
ON dim_stock(industry_l1, code);

-- 只看有在线明细的股票
CREATE INDEX idx_stock_has_detail_industry
ON dim_stock(has_detail, industry_l1, code);

-- 行业在日期范围内的趋势；主键 (industry_l1, date) 已覆盖

-- 某日比较所有行业
CREATE INDEX idx_industry_daily_date
ON fact_industry_daily(date, industry_l1);

-- 某日比较所有因子
CREATE INDEX idx_factor_ic_date
ON fact_factor_ic_daily(date, factor_name);

-- 最近质量运行
CREATE INDEX idx_quality_run_started_at
ON fact_data_quality_run(started_at DESC);
```

索引原则：

- `(code,date)` 适合 `WHERE code=? AND date BETWEEN ? AND ?`。
- `(date)` 适合某天全市场截面。
- `(industry_l1,code)` 适合行业筛选。
- 不为每个因子列建索引；因子分析依赖预聚合表或逐股小范围数据。
- 避免既有 `UNIQUE(code,date)` 又创建相同列顺序的普通索引。
- 发布数据库后执行 `ANALYZE`，并用 `EXPLAIN QUERY PLAN` 验证查询是否使用索引。

### 5.3 SQLite 运行方式

- Streamlit 以只读 URI 打开：`file:demo.db?mode=ro`。
- 每个查询短连接，用完关闭；不要把可变全局连接跨用户缓存。
- 公开数据库在离线发布阶段完成写入、校验、`ANALYZE` 和压缩。
- 若数据库只读，不需要在网页运行时启用 WAL。
- 所有筛选参数用 `?` 占位符绑定，列名和排序字段使用白名单。

## 6. Streamlit 性能优化方案

### 6.1 缓存什么

#### 缓存长期稳定的小数据

```python
@st.cache_data(ttl=3600, max_entries=4, show_spinner=False)
def load_stock_catalog(data_version: str) -> pd.DataFrame:
    ...

@st.cache_data(ttl=3600, max_entries=4, show_spinner=False)
def load_asset_summary(data_version: str) -> dict:
    ...

@st.cache_data(ttl=1800, max_entries=16, show_spinner=False)
def load_industry_summary(start_date: str, end_date: str, data_version: str):
    ...
```

适合缓存：

- 股票目录、行业列表、数据版本与 manifest。
- 首页 KPI 和最新一日市场快照。
- 行业日度汇总、市场宽度、质量趋势。
- 因子 IC 汇总和模型/回测摘要。

#### 缓存带参数的明细查询

```python
@st.cache_data(ttl=900, max_entries=128, show_spinner=False)
def query_stock_history(code: str, start_date: str, end_date: str,
                        data_version: str) -> pd.DataFrame:
    ...
```

缓存键必须包含：股票代码、开始/结束日期、所需列、数据版本。这样数据包更新后，只需改变 `data_version`，旧缓存自然失效。

#### 不建议缓存的内容

- 不用 `st.cache_resource` 常驻整张 50 万行 DataFrame。
- 不缓存用户当前选择或自选股；这些放 `st.session_state`。
- 不优先缓存 Plotly 图对象；先缓存图表输入的聚合 DataFrame，再按主题快速组装图。
- 不缓存数据库写连接。
- 不用无限 TTL 缓存“最新数据”。

### 6.2 数据加载策略

#### 启动时

只加载：

- `manifest`/数据版本。
- `dim_stock` 的必要列。
- 首页预聚合 KPI。
- 最新质量状态。

不加载：

- 全部股票的所有日线。
- 50 列因子宽表。
- 全部情绪记录。
- 逐日持仓与模型预测明细。

#### 用户选择股票后

执行类似查询：

```sql
SELECT date, open, high, low, close, volume, amount,
       ret, ma5, ma20, rsi, macd, volatility_20d, sentiment
FROM fact_stock_daily_demo
WHERE code = ?
  AND date BETWEEN ? AND ?
ORDER BY date;
```

默认查询近 252 个交易日；用户主动切换时才扩大到 3 年，并设置最大日期跨度。

#### 用户进入行业/市场页面后

直接查 `fact_industry_daily` 或 `fact_market_daily`，不从逐股宽表临时 `groupby`。

#### 用户进入因子页面后

默认查 `fact_factor_ic_daily`。只有选择单只股票时，才查询其因子明细；相关性矩阵在离线阶段按固定因子集生成，或只对当前股票的小数据计算。

### 6.3 代码结构调整

把当前单文件 `app_pro.py` 逐步拆成：

```text
app.py                         # 页面入口与路由
app/
├── data_access.py             # 参数化 SQLite 查询与缓存
├── metrics.py                 # KPI 口径和展示格式
├── charts.py                  # Plotly 图表函数
├── ui.py                      # 主题、卡片、来源标签
└── pages/
    ├── asset_overview.py
    ├── market_dashboard.py
    ├── stock_profile.py
    ├── industry_factor.py
    ├── data_quality_lineage.py
    ├── sql_explorer.py
    └── research_validation.py
```

不要一次性重写。先抽 `data_access.py`，让原页面改用新查询函数；功能稳定后再拆页面。这样回归风险最小。

### 6.4 分页策略

- Streamlit 表格默认只返回前 100～500 行。
- 公开 SQL 查询强制 `LIMIT 500`。
- 普通列表可使用页码，每页 50 行。
- 若数据量扩大，使用游标分页：`WHERE (date, code) > (?, ?) ORDER BY date, code LIMIT ?`，避免大 `OFFSET`。
- 图表不做分页，而是按日期/行业预聚合后返回有限点数。

### P0-1：数据资产与质量监控

价值：是最符合数据分析岗位的页面，业务方无需理解模型就能看懂。

## 12. 面试时如何介绍升级

### 12.1 60 秒版本

> 第一版为了稳定部署，把 50 只股票的因子数据整体读入 Streamlit。后来我按照真实数据产品的思路做了二次优化：把数据拆成全市场资产目录、离线聚合指标和按需查询明细三层。启动时只读元数据和首页 KPI，股票、行业、因子明细通过带索引的 SQLite 参数化查询获取，并使用带数据版本的 `st.cache_data` 缓存。市场、行业、质量和因子 IC 在离线发布阶段预计算，因此网页不再扫描 50 万行宽表。公开版对真实研究规模、在线演示规模和合成数据口径分别标识，既保留业务真实性，也避免分发原始行情和模型资产。

### 12.2 被问“为什么不用更高级数据库？”

> 当前数据量和只读 Demo 场景下，SQLite 的部署成本最低，50 万行通过组合索引、预聚合和按需查询完全够用。我重点展示的是数据模型和查询模式，而不是为了技术栈数量引入运维负担。如果扩展到分钟/Tick 级、多人并发和长期增量写入，我会把明细层迁移到 ClickHouse/Doris，维度和汇总层仍保持相同业务模型。

### 12.3 被问“为什么公开版还是合成数据？”

> 这是主动的数据发布治理设计。完整研究环境使用真实数据，但公开层只发布合规元数据、汇总指标、研究运行清单和确定性合成明细，Token、逐日原始行情、模型权重与持仓不发布。页面分别显示研究覆盖和在线演示覆盖，不混写口径。

### 12.4 被问“优化前后有什么量化变化？”

需要在改造完成后用实际基准回答，例如：

```text
优化前：启动读取完整宽表，内存 X MB，首页 Y 秒，切换行业页 Z 秒。
优化后：启动只读取元数据/汇总，内存下降 N%，首页 P 秒，逐股查询 Q ms。
```

不要提前编造这些数字。把基准脚本和结果 JSON 提交到仓库，面试时展示真实对比。
